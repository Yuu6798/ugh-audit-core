## 公開前に埋める条件

- [x] [データ取扱い・削除方針](data-policy.md)の非公開窓口を運営者が指定する：`kkoo6798@gmail.com`。
- [ ] 同窓口の受信・返信確認、担当者、適用開始日を確定する。
- [ ] 監査30日・本人確認後7日以内の削除・バックアップ消去期限を、実際の保存先一覧と照合する。
- [ ] 自動日次削除を本番で有効化し、起動時の清掃結果・次回期限と停止→清掃→再開の検証結果を記録する。
- [ ] 利用上限台帳、無効招待、問い合わせ記録、旧キャッシュの処分を運用へ組み込む。owner不明の旧記録は別管理する。
- [x] PR #119のCI・セルフレビューを完了し、修正版を本番へ反映した証拠を上表に記録する。
- [ ] TLS終端・ホスト・クライアントの秘密ヘッダー保護、実プランのログ条件、バックアップ一覧を確認する。
- [ ] 利用者が許可したBYOK・モデル・費用上限を決め、下記の実監査1件を確認する。
- [ ] 問い合わせ先、外部MCPの招待条件、モデル料金、権利条件と掲載終了後の未確定事項を掲載文・ZIPで一致させる。
- [ ] 運営者が掲載保留の解除と提出内容を確認する。未確定項目があれば公開しない。

運営者は今回の合成監査1件に限り自分のキー利用を許可した。一般利用者のBYOK必須・共通キーへの
代替禁止・掲載保留は変わらない。実行結果は確認後に追記する。未確定事項は実監査の結果と、
自動削除の本番受入、削除依頼の受付・本人確認・返信の運用受入である。
運用案や制御応答の試験を実環境での成功に置き換えない。キーをチャット・公開資料へ貼らない。

## 公開前の実モデル監査1件

事前条件：検証する本人が所有するAnthropicキーをクライアントの秘密設定から渡し、使用モデル、
1件の実行、最大呼出回数・費用上限を合意する。自動再試行やキーの代替をしない。
認証確認だけで有料監査を開始しない。支出制御はプロバイダー側も確認する。

1. 選定済みのCodexクライアントへ、リポジトリ版スキルとUGHの招待・BYOK設定を渡す。
   Agensiの未公開スキル取得とは区別する。
2. [利用開始ガイドの合成2要件](getting-started.md#2-2件の要件で試す)を1件だけ監査する。
   `auto_generate_meta=false`、専用の合成session IDを使い、個人情報を入力しない。
3. 要件別根拠、充足・欠落、最終判定、使用モデル・プロバイダー結果を確認する。
   タイムアウト・認証失敗・unknownは成功に数えない。失敗しても追加呼出は予算を確認してから行う。
4. 保存IDを同じ利用者の履歴とID取得で再取得する。別利用者からは本文を取得できないことを確認する。
   必要なtext/CSV出力も保存結果と照合する。
5. UTC時刻、コミット・デプロイ、クライアント版、合成入力、監査ID、判定・確認項目、実際の費用または
   プロバイダー側の計測状況を、秘密を除いた検証記録へ残す。キー、秘密ヘッダー、実利用者の履歴は含めない。

この1件は接続・保存の疎通確認であり、精度保証ではない。要件自動生成の実モデル経路を試していなければ、
その未確認範囲も記録する。必要な別試験は、追加のキー利用・費用条件を決めてから行う。

## 提出直前と公開後

無料掲載は外部MCPのホスティングやモデルの無料枠を含めない。接続テンプレートと運営者向けの
セットアップ手順をZIPへ同梱し、[掲載案](../marketplace/agensi/listing-draft.md)・
[配布条件](../marketplace/agensi/rights-and-withdrawal.md)と整合させる。
掲載終了後に既存利用者が保持するAgensi側のアクセス権は未確定のため、その不確実性を公開判断に含める。

公開直前の成果物は、検証対象コミット、PR・CI・レビュー結果、ZIPのファイル一覧とハッシュ、
掲載文、実監査の証跡、適用開始できる運用方針、残存する制約を揃えた判断資料とする。
この準備作業はCreator Mode有効化、審査提出、Live化を自動的に許可しない。

明示的な公開判断後、AgensiでLiveになってから、別の確認として
`get_skill` → 対応クライアント → UGHの監査を実行する。追加モデル呼出も許可された予算内で行う。
この一連の成功を記録するまでは「Agensi対応確認済み」と表示しない。
