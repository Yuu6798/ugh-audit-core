# 招待ベータの配備前処理

`python -m ugh_audit.deployment start` は、永続ボリューム、招待台帳、DBを検査してから
uvicornを起動する。失敗した場合はHTTPサーバーを起動しない。
`UGH_RETENTION_AUTOMATION=1` では、親プロセスが子のuvicornを管理して日次清掃する。
この設定時は直接のuvicorn起動を拒否する。自動化を使わない既存のPython APIは変更しない。

## 環境変数を正とする招待台帳

`UGH_INVITES_JSON` を指定した場合、**毎回の起動でその内容を招待台帳へ適用する**。
内容は `ugh_audit.invites` とHTTP認証が使う台帳形式と同じで、SHA-256だけを格納する。
平文のBearerキーをこの変数に入れない。重複キー、未知フィールド、不正な型、
空のusers、重複ハッシュ、262,144bytes超過は拒否する。

**この運用では、失効・更新は環境変数側で行う。台帳だけを書き換えても再起動時に元へ戻る。**
利用者を失効させる場合は、そのuserの全credentialを環境JSONで `enabled:false` にし、
配備を反映する。ローテーションも環境JSONで古いcredentialを無効にし、新しいハッシュを追加する。
配備が完了するまでは変更が適用されない。変更後に古いキーが401になることを確認する。
`UGH_INVITES_JSON` が存在するプロセスではCLIのissue/revokeを拒否し、環境JSON更新と
再配備を案内する。オフラインでCLIを使って台帳を作る場合はこの変数を明示的に外し、
完成したハッシュ台帳を環境変数へ反映する。ファイルだけの編集を失効完了と扱わない。

環境JSONは一時ファイルで検証後、0600のファイルで `UGH_INVITE_FILE` をatomic replaceする。
不正な環境JSONは既存台帳・DBを変更しない。JSONやハッシュ、キー、監査本文はログに出さない。
`UGH_INVITES_JSON` を設定しない場合は既存の台帳を検証して維持し、CLIによる失効を継続できる。

## Railwayの設定

| 設定 | 用途 |
|---|---|
| `RAILWAY_VOLUME_MOUNT_PATH` | Railwayが付与する実際の永続マウント先 |
| `UGH_ACCESS_MODE=invite` | 招待認証。Railwayでlocalは拒否 |
| `UGH_AUDIT_DB=/data/audit.db` | 既存監査DB |
| `UGH_USAGE_DB=/data/usage.db` | 利用回数・同時実行予約の永続台帳 |
| `UGH_INVITE_FILE=/data/invites.json` | 検証したハッシュ台帳の保存先 |
| `UGH_INVITES_JSON` | 必要な場合だけ指定する、正となるハッシュ台帳JSON |
| `UGH_ALLOWED_HOSTS` | MCPに許可する公開Host値 |
| `UGH_ALLOWED_ORIGINS` | ブラウザクライアントを使う場合に許可するOrigin |
| `ANTHROPIC_API_KEY` | 公開inviteサービスでは未設定または空。監査は利用者のBYOKを使う |
| `UGH_AUDIT_EMBED_CACHE_DISABLE=1` | 公開ホストの永続埋め込みキャッシュを無効化する追加設定 |
| `UGH_RETENTION_AUTOMATION=1` | POSIX単一ホストで、停止確認付きの日次清掃を有効にする |

各監査は招待Bearerとは別の `X-UGH-Anthropic-Key` ヘッダーを要求する。
サーバー環境にAnthropicキーが誤って残っていても、公開監査の代用には使わない。
利用者キーは環境変数、招待台帳、DB、バックアップ、監査本文、アクセスログに保存しない。
TLS終端・監視・エラー収集でも両方の秘密ヘッダーを記録しない設定にする。
公開監査の要件生成は共有メタデータキャッシュを使用しない。
HTTP監査の埋め込みも共有永続キャッシュを迂回する。設定変更だけでは旧キャッシュを消さないため、
[データ取扱い・削除方針](data-policy.md)に従って停止中に対象ファイルを確認する。
モデルAPI料金は利用者自身のAnthropicアカウント、ホスト料金は運営者に発生する。
クライアント設定とエラーの契約は [招待制ベータの運用](invite_beta.md) を参照する。

Railwayの識別変数がある場合は、マウント先が存在し、OSのmount情報でも確認できることが必須。
DB・台帳・バックアップはそのマウント配下に置く。通常ディレクトリを `/data` と名付けただけでは
通過しない。SQLiteの本体・WAL・SHM・journal、招待台帳、lockのパス衝突も拒否する。

既存監査DBが見つからない場合は起動を止める。空DBを意図して作る初回環境に限り
`UGH_ALLOW_NEW_AUDIT_DB=1` を指定できる。既存環境のボリューム不備をこの設定で回避しない。
初回の利用台帳は作成する。既存利用台帳の内容を消去・初期化して上限を返却することはない。

## バックアップと移行

移行は、旧プロセスが監査DBへ書き込まない配備時間帯に行う。単一ホストの同じ永続ボリュームを使う。
前処理同士はOSの排他lockで直列化され、プロセス終了時にlockを解放する。

既存schemaの変更が必要なときだけ、SQLite backup APIで `deployment-backups/` へ
0600の新規バックアップを作り、`PRAGMA integrity_check` を通す。稼働中のWALにある
コミット済み行もバックアップ対象になる。既存バックアップを上書きしない。
次にバックアップのコピーを `AuditDB` で移行し、元の全列・全行が変わらず、
所有者列のなかった旧行がNULLのままであることを検証してから本体を移行する。
一時的に本体・バックアップ・検証コピーの容量が必要になる。

同じschemaへの移行が完了した後の通常再起動では追加バックアップを作らない。
検証失敗時は元DBと作成済みバックアップを残し、起動を止める。未解決の移行を繰り返し
起動するとバックアップが増えることがあるため、固定エラーコードを確認してから再試行する。
古い `quality_score` / `verdict` のbackfillが元の値を変える場合も自動で進めず、個別確認を求める。

既存の利用台帳は現行schemaと時計行を検証し、カウンタと予約を維持する。
未知・不完全な利用台帳schemaの自動移行は行わず、`usage_database_schema_unsupported` で止める。
将来の利用台帳schema変更には別途バックアップ付き移行が必要。

ログの `deployment_backup_created` はバックアップ作成を、`deployment_prepared` は前処理完了を示す。
後者には `audit_migration`、`audit_rows`、`integrity`、`backups`、`volume_verified` を含める。
エラーは `deployment_failed` と固定の `code` だけを出し、秘密設定や監査本文を含めない。
前処理完了・health成功の後も、匿名401、認証履歴200、別user隔離、失効401、
MCP接続、APIキーなしの監査拒否、利用者BYOKでの意味照合を別途確認する。
モデル呼出は承認済みの利用者キーと予算で行う。自動復元は行わない。

## 日次削除の自動化

POSIX環境で `UGH_RETENTION_AUTOMATION=1` と上記startコマンドを使う。初回は旧サーバーを
完全に停止してから切り替える。単一ホスト・単一ボリューム・単一サービスが前提で、同じDBへ
別のPython/uvicornプロセスを接続しない。Railwayではvolume付きの1 replicaを使用する。

起動時に清掃し、前回の清掃開始から23時間後に次の停止を開始する。
以降は停止・清掃を含め前回起点から24時間以内に完了する条件で、次の処理を実施する。

1. 稼働中の子へ終了を通知し、停止・回収を確認する。最大30秒の猶予を超えたら強制停止して異常終了する。
2. owner付きの29日以上経過した監査、期限切れ利用台帳、既知の旧キャッシュを清掃する。
3. 登録済みの移行バックアップは保持起点から29日以上経過したものを消去する。
4. 全処理成功後だけ子を再起動し、次の期限を設定する。失敗時は受付を再開しない。

清掃・再起動中は短い停止時間が生じる。期限監視には単調時計とUTCを使い、時計の逆行や
1時間の余裕を超える処理も異常とする。Railwayの自動再起動は再び起動前清掃を行うため、
「一度失敗したら人手で解除するまで永久停止」という仕組みではない。
`/data/audit.db.retention.json` は直近成功の結果・件数・次の期限をatomicに記録する。
監査本文、owner ID、APIキーは記録しない。運営者は失敗ログと期限超過を確認する。

runtime lockは親と子の生存期間中保持され、別のstartや孤児プロセスとの重複を防ぐ。
子も独立した監視threadを持ち、親の喪失、時計の逆行、清掃起点から23時間30秒の期限で
自分へSIGTERMを送り、終了しなければさらに最大30秒でprocess groupを強制停止する。
この監視はHTTPの終了処理が終わっても残存workerがいる間は続き、ログ出力の完了を待たない。
親が異常終了した場合も子の実終了までlockを保持し、次の起動は必ず起動前清掃を行う。
手動CLIの `--service-stopped` は停止検出ではないため、手動削除・復元では親子の両方を止める。
Windowsでこの自動化を有効にした起動は拒否する。Windowsでは従来の停止中CLIを使う。

## 既存バックアップの登録と対象範囲

新しい移行コピーには内容のSHA-256、サイズ、保持起点を記すmanifestを併置する。
mtimeやコピーし直した日で期限を延ばさない。未知ファイル、リンク、内容の変化、未登録コピーは
自動削除せず起動を止める。旧コピーは自動化OFFで内容・作成証拠を点検し、次の形式で登録する。

```bash
python -m ugh_audit.managed_files adopt-legacy --directory /data/deployment-backups \
  --name audit-before-EXACT_ID.sqlite --retention-origin VERIFIED_UTC_LOWER_BOUND \
  --expected-size VERIFIED_BYTES --expected-sha256 VERIFIED_SHA256
```

実際の名前・サイズ・ハッシュと、作成日時以前と確認したUTC日時へ置き換える。旧コピーの起点は
正確な作成日時と区別して記録する。登録はファイル内容を変更・削除しない。
キャッシュ清掃はDB配下の既知形式だけを対象とし、ディレクトリを再帰削除しない。

無効招待、問い合わせ記録、運営者の別エクスポート、クラウドバックアップはこの自動化の対象外。
[データ取扱い・削除方針](data-policy.md)の一覧で別途管理する。復元時は削除記録と現在の期限を
再適用してから受付を再開する。実環境の証拠は[公開前チェック](beta-release-checklist.md)へ記録する。
