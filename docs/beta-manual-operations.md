## 招待時に用意する非公開台帳

招待発行前に、連絡先へ確認を送り、その連絡経路を本人が利用できることを確認する。
非公開の対応表へ `owner_id`、登録連絡先、確認日時、招待発行日、利用終了日、
適用した方針版を記録する。連絡先は現在の `invites.json` schemaへ追加せず別台帳で管理する。
owner IDは別人へ再割当てしない。過去の招待に対応表がない場合は、発行時の記録から
確認できるまで一般招待を開始せず、申告者へそのownerを割り当てない。

実台帳・依頼記録はアクセスを主担当に限定した私有保存先に置く。公開リポジトリ、ZIP、
共有作業メモ、公開Issueへ保存しない。APIキー・招待トークン・監査本文は記録対象外。
バックアップや同期先を増やす場合は、保存先一覧と消去期限にも追加する。

## 受付から完了まで

1. **受付**：受信時刻をUTCで記録し、返信にはJSTも併記する。受付番号、登録連絡先、
   希望範囲だけを扱う。監査IDは範囲指定には使えるが本人確認には使わない。
   初回返信で所要手順を案内し、APIキー・招待キー・監査本文を送らないよう伝える。
2. **照合**：非公開台帳の登録連絡先とownerを照合する。新たに申告された連絡先や
   メールのFrom表示だけで本人と判断しない。不明な相手へ履歴の有無やowner情報を返さない。
3. **確認コード**：既知の登録連絡先にだけ、依頼番号と結びつく無作為な一回用コードを送る。
   128 bit以上、有効24時間、3回失敗で無効という手動手順案とする。既知の連絡先からの
   正しい返信と依頼番号・希望範囲を照合して確認済みにする。照合用のハッシュ・期限は
   私有一時記録だけに置き、利用後または失効後に破棄する。コードを含む送受信メールも
   自分が管理するコピーから消去し、受付台帳には確認成否と日時だけを残す。
4. **範囲合意と期限**：全履歴の場合は「削除実施時点までの本人の全履歴」と確認する。
   本人確認完了時刻から7×24時間以内が本体削除の期限。範囲が未確定でも確認済みの
   時計を再設定せず、主担当が早期に調整する。招待終了・失効の希望は履歴削除と別に確認する。
5. **実行予約**：確認後3日以内を内部目標に手動枠を予約し、保守停止の予定を通知する。
   5日経過時点で未完了なら主担当が臨時枠・代行・遅延通知を判断する。
6. **削除と検査**：下記のオフライン手順で対象・件数・整合性を確認する。
   同じownerの削除対象件数が0、他ownerと旧NULL行の保持、当日上限が維持されていることを
   確認する。モデル監査を再実行して検査しない。
7. **本体完了の返信**：実際の完了日時・対象範囲・件数、バックアップの残存有無と期限を通知する。
   バックアップ未処理なら「全て消去済み」と書かない。外部提供者や本人の保存先は対象外と明示する。
8. **全体完了**：管理するコピーの期限処理を確認して完了返信とする。受付台帳を完了から90日後に
   削除する予定を入れる。復元に必要な削除記録を、それに関係するコピーが残る間に先に消さない。

確認ができない場合は削除しない。既知の経路に7日後一度だけ確認し、受付から14日で未確認のまま
保留終了を通知する案とする（未知の相手には登録の有無を漏らさない）。後日確認できれば再開し、
その確認時点から7日を計算する。連絡先を失った場合は元の招待発行記録など独立した証拠を
主担当が確認する。APIキー、招待キー、身分証画像を代替として収集しない。

**特定IDだけの依頼**：現行CLIはowner全体または期間の削除に限る。勝手に全履歴へ広げない。
本人が全履歴削除へ明示同意した場合だけ標準手順へ進む。それ以外は主担当がownerと対象IDを
限定した個別手順を合成DBで検証してから実施する。未検証のSQLを本番へ貼らない。
7日期限を守れない見込みなら早期に制約と予定を通知する。この経路は標準CLIで確認済みとは表示しない。

## Railwayで手動削除するときの切替案

対象は既存productionの単一service・単一volume `/data`。**この切替案は本番未実演**であり、
本書作成時に配備変更・削除は行わない。初回は合成データの別環境で同じ切替を確認してから使う。
CLIの削除・他owner保持・復元後の再適用は既存の合成DB試験で確認済みだが、ホスト切替とは区別する。

1. 主担当が既存commit、config path、start、healthcheck、restart、volume ID・mount、replica、
   自動配備設定を私有の作業記録へ控える。自動配備を止め、待機中の配備・rolloutがないことを確認する。
   同じvolumeへ別サービスを並行接続しない。コピーによる無期限の退避を作らない。
   **開始条件**：直近の自動清掃成功日時・次回期限と、各バックアップ/エクスポートの期限を照合する。
   HTTPなしの保守中は自動清掃も止まる。最大2時間の保守枠に切替・復帰・清掃の余裕を足しても
   最も早い期限より前に終えられる場合だけ開始する。期限が枠内に来るなら先に通常の清掃を
   完了して成功記録・次回期限を再確認し、期限が近い別コピーも先に処理する。
   停止中の待機・障害を理由に期限を延ばさない。作業中も主担当が最も早い期限を監視し、
   予定を超える場合は受付停止を維持して期限処理を優先する。単に2時間待てる設定は期限保証ではない。
2. 同じservice・volumeで、承認済みrevisionの
   [`/deploy/railway-maintenance.json`](../deploy/railway-maintenance.json) をcustom config pathとして
   手動配備する。HTTPを起動せず、healthcheckなし・自動再起動なし・最大2時間の待機だけを行う。
   このJSON方式は既存の旧Config as Code対応serviceだけが対象。新規検証serviceへそのまま
   適用できると想定せず、下記の方式・期限を確認する。
   通常の `railway.toml` は `/health` を要求するため、dashboardのstartだけを変更しない。
   deployment detailsで実際の設定が一致することを確認する。追加のpre-deploy hookは無効化しておく。
3. 旧配備の終了、replica 1、正しいvolume mount、HTTP・supervisorの不存在を確認する。
   `UGH_RETENTION_AUTOMATION=0` への変更だけ、子HTTPだけのkill、502応答だけでは停止確認にならない。
   PID1の親をkillした同じコンテナで作業継続しようとしない。
4. メンテナンス配備のprivate consoleで既定のdry-runを実行する。例の `CONFIRMED_OWNER` を
   受付台帳で確認したownerへ置き換える。結果には件数だけを残し、端末の共有・録画に注意する。

```bash
python -m ugh_audit.retention --db /data/audit.db --owner CONFIRMED_OWNER
# 正しい対象・全プロセス停止・範囲同意を確認した後だけ実行する。
python -m ugh_audit.retention --db /data/audit.db --owner CONFIRMED_OWNER --apply --service-stopped
python -m ugh_audit.retention --db /data/audit.db --owner CONFIRMED_OWNER
```

5. `deleted_audits` とdry-run件数、再dry-runの `matched_audits=0`、DB整合性、他owner/旧NULL行の
   保持を照合する。失敗、とくに `deletion_committed=true` では受付を再開せず、状態を点検する。
   複数DBとバックアップは一括transactionではない。全体成功を推測しない。
6. バックアップ台帳を更新し、必要な期限処理を行う。通常のconfig pathへ戻して既存
   `python -m ugh_audit.deployment start` を配備し、日次自動化をONのまま起動前清掃を通す。
   health、匿名拒否、失効状態、履歴境界、当日利用枠をモデル不要の方法で確認して再開する。
   最後に自動配備設定を元に戻す。2時間で待機が終了した場合も、点検なしに通常配備へ戻さない。

configのコード設定はdashboardより優先され、custom config pathを指定できる
（[Railway公式設定資料](https://docs.railway.com/config-as-code)）。
volume付きserviceは旧配備と新配備の同時mountを防ぐため停止時間を伴う
（[公式healthcheck資料](https://docs.railway.com/deployments/healthchecks#services-with-attached-volumes)）。
これらの仕様は今回の本番切替成功の証拠ではない。実施時の状態とmountを必ず照合する。

## 自動化の対象外記録・バックアップ・復元

| 対象 | 主担当が行う処理 |
|---|---|
| 無効招待と登録連絡先対応表 | 利用終了日時・除去期限を記録し30日以内にcredential/不要な連絡先を除去。未完の削除対応に必要な最小情報だけ受付台帳へ移し、完了後90日で削除 |
| 招待の設定元 | productionの `UGH_INVITES_JSON` と展開先fileを整合。fileだけの失効では次回配備で復活し得る。owner IDは再利用せず、再発行時も旧tokenを再利用しない |
| 問い合わせ・返信 | 受付台帳、受信/送信/下書き/Trash等の自分が管理するメールコピーを同じ完了後90日の一覧へ登録。秘密や不要な添付は残さない |
| エクスポート・クラウドコピー | 作成日時・保存先・期限を登録。作成後30日と本体削除後30日の早い方。存在確認できないコピーを「なし」としない |
| 旧NULL ownerの18件 | 11月1日10:00 JSTまでの棚卸し案。主担当が保有理由・処分期限・確認方法を記録し受け入れる。申告者へ割当てず、今回の手順だけで自動削除しない |

バックアップは登録済みコピーだけが自動清掃対象。別コピーを日次処理が消すと想定しない。
本体削除後に対象データを含む新しいコピーを作らず、コピーや復元で期限を延長しない。
例：11月4日12:00 JSTに本体削除、11月1日12:00 JST作成のコピーなら、
期限は作成後30日の12月1日12:00 JST（本体削除後30日の12月4日より早い）。これは記入例で実績ではない。

復元中は受付を止める。**そのバックアップ取得時点より後に完了した削除**と現在の保持期限を再適用する。
削除後に作られたバックアップへ過去のowner全削除を機械的に再適用すると、その後の正当な新規監査まで
失うため行わない。取得時刻・範囲が不明な場合や個別ID削除の場合は停止したまま個別手順を検証する。
招待失効・利用上限・復元後の期限清掃を確認してから受付を再開する。
