# はじめて使う方へ

UGH Audit Coreは、**指定した指示・制約が回答文に書かれているか**を要件ごとに確認します。
たとえば「金曜日までに提出する」「PDFで添付する」という2件の指示を、案内文が伝えているかを
点検できます。事実の正確さ、文章全体の品質、実際に提出されたか、要件リストの網羅性は判定しません。
まずは短い日本語の案内文と、人が確認した2〜5件の要件から始めてください。

## 使い方を選ぶ

| やりたいこと | 最初に用意するもの | 次に読む場所 |
|---|---|---|
| 招待されたサービスをMCPから使う | 運営者からの接続先・招待トークン、自分のAnthropic APIキー、対応MCPクライアント | このページの「招待された利用者」 |
| 自分でサーバーを動かす・開発する | Python 3.10以上、リポジトリ、隔離した開発環境 | このページの「自分で運営・開発する方」 |

一般公開のセルフサインアップはありません。利用先の運営者から招待と接続案内を受け取ってください。
リポジトリの公開は、稼働サービスの利用権やモデルAPIの無料枠を提供するものではありません。
Agensi経由のスキル取得から監査までの一連の動作は未検証です。

## 招待された利用者

### 1. 接続と費用を確認する

クライアントにはStreamable HTTPと、次の2つの秘密HTTPヘッダーを設定できる機能が必要です。
接続先は運営者が案内するHTTPSのMCPエンドポイントを使います。

| ヘッダー | 用途 |
|---|---|
| `Authorization` | `Bearer <招待トークン>`。利用者の識別と履歴の分離 |
| `X-UGH-Anthropic-Key` | 利用者自身のAnthropic APIキー。要件の意味照合と任意の要件生成 |

キーはクライアントの秘密設定に登録し、チャット・ツール引数・監査本文・リポジトリへ貼り付けません。
招待トークンだけでもMCPの初期化、ツール一覧、履歴取得はできますが、監査には両方が必要です。
クライアント固有の設定と認証の詳細は、[招待制ベータの運用](invite_beta.md)と
[接続設定の注意点](../marketplace/agensi/ugh-instruction-audit/references/connection.md)を参照してください。

**明示した要件でもモデル呼び出しがあり、API料金は自分のAnthropicアカウントに発生します。**
要件の自動生成を無効にしても無料・オフラインの監査にはなりません。サービスの利用上限と、
プロバイダー側の支出設定を確認してください。サーバー運営者のキーによる代替は行いません。

APIキーは監査サービスを経由してAnthropicへ送られます。監査本文は運営者に渡り、要件と回答は
Anthropicで照合されます。アプリはキーを履歴に保存しませんが、確定した監査結果は保存されます。
信頼する運営者の接続先を使い、[保存期間・削除方法](data-policy.md)を確認してください。
現在は運用案で、窓口の受信確認・日次作業の受入確認が未完了です。一般の招待開始を保留しています。
個別の監査・削除依頼は公開Issueへ送らず、[データ方針に記載した非公開窓口](data-policy.md#削除依頼問い合わせ窓口)で扱います。

### 2. 2件の要件で試す

以下は架空の案内文を使った入力例です。接続後、`audit_answer` ツールに次の引数を渡します。
キーは含めず、要件を人が明示して `auto_generate_meta` を `false` にしています。

```json
{
  "question": "申請書の提出案内を作成してください。",
  "response": "申請書は金曜日の17時までに担当窓口へ提出してください。",
  "question_meta": {
    "core_propositions": [
      "申請書は金曜日の17時までに担当窓口へ提出する",
      "申請書はPDF形式で添付する"
    ]
  },
  "auto_generate_meta": false,
  "session_id": "first-audit-example"
}
```

この案内文にはPDF形式の指定がありません。照合で1件の充足と1件の欠落が確定した場合の
主要フィールドは次のようになります。**仕様説明用の抜粋であり、実行記録や結果の保証ではありません。**

```json
{
  "verdict": "rewrite",
  "requirement_verdict": "incomplete",
  "C": 0.5,
  "requires_review": true
}
```

実際の結果では `assessment_context` で使われた要件を確認し、`semantic_matching` の
要件別の状態・引用・理由を読みます。修正する場合はPDFの指定を案内文へ加え、人が内容を確認して
再監査します。入力項目と完全な出力契約は[REST・MCP API仕様](server_api.md)にあります。

### 3. 判定を読む

| 結果 | 意味と次の行動 |
|---|---|
| `accept` | 有効な全要件の記載が確認された。要件自体の妥当性と最終利用判断は人が確認する |
| `rewrite` | 欠落または矛盾が確認された。要件別の根拠を読んで回答文を修正する |
| `degraded` | 判定できない要件がある、要件がない・不正、または照合に失敗した。合格や不合格と扱わず原因を確認する |
| `requires_review=true` | 人の確認が必要。AI生成の要件を使った場合は、`accept` でもこの値になる |

`C` は全要件を判定できた場合の記載充足率です。確認不能があれば `null` になり、0点という意味では
ありません。上位の `S`・`delta_e`・`quality_score` も現行仕様では `null` です。旧指標の
`legacy_metrics` は合否に使いません。[判定契約と限界](semantic_matching_v2.md)を参照してください。

保存された結果は `get_history` に `{"limit": 5}` を渡して確認できます。招待利用者の履歴は
所有者ごとに分離され、同じ `session_id` を使っても他の利用者の履歴は見えません。
`degraded` は通常の監査履歴に保存されませんが、開始した監査は利用上限を消費します。

## 接続・実行に困ったら

通信やツール実行のエラーと、回答文に対する `verdict` は別です。MCPクライアントによっては
HTTP状態ではなくツールエラーとして表示されます。

| 表示・状態 | 確認すること |
|---|---|
| 401、`authentication_required`、`invalid_credential` | 招待トークンの設定、有効期限、失効を運営者に確認する |
| `provider_key_required` / `invalid_provider_key`（RESTは400） | 自分のAPIキーが秘密ヘッダーに設定されているか確認する。値そのものは共有しない |
| 429 | 利用上限。`Retry-After` またはエラーの待機案内に従う |
| 503 | サーバー設定や利用台帳の問題。運営者へエラーコードを伝える |
| `degraded` | 要件・要件別の理由・エラーを確認する。API拒否やタイムアウトも成功として扱わない |

認証と利用上限は[招待制ベータの運用](invite_beta.md)、実行時の調査は
[トラブルシューティング](troubleshooting.md)を参照してください。

## 自分で運営・開発する方

Python 3.10以上と仮想環境を用意し、[README](../README.md)のインストール手順から始めます。
サーバー実行用は `.[server]`、開発・テスト用は `.[dev]` です。外部へ提供する場合はHTTPS、
招待台帳、永続DB、利用上限を設定し、モデル呼び出しには利用者自身のBYOKを使います。

設定・起動は[招待制ベータの運用](invite_beta.md)、永続ボリューム・バックアップ・移行は
[配備手順](invite-beta-deployment.md)へ進んでください。`UGH_ACCESS_MODE=local` は
信頼する端末のloopback開発用で、公開サービスの認証を省略する設定には使いません。
開発用の直接Python・CLI呼び出しと、HTTP経由のBYOK設定は区別してください。
[データ取扱い・削除方針](data-policy.md)と[公開前チェック](beta-release-checklist.md)を埋めてから招待を開始します。

ソースやテストを読むだけなら有料モデル呼び出しは不要です。リポジトリのpytestは外部通信を
遮断したテスト用応答・保存済み応答で検証します。これは本番プロバイダーへの実接続成功や、
未知の文章に対する精度を保証するものではありません。
