**状態：公開前の運用案（2026-10-30 JST更新）。対外的な適用開始日は未設定。**
監査履歴30日、本人確認後7日以内の削除、バックアップからの消去は削除後30日以内という案を
運営者が選択し、日次削除の自動化を指示した。下記窓口の担当者・運用受入と本番確認が揃うまで、
この案を稼働中の保持期限として約束せず、掲載と一般の招待開始を保留する。
自分でホストする場合は、その運営者の実際の設定・窓口・保存先に合わせて別途案内する。

提供者の本番ホストでは2026-10-29 15:08 UTCに日次自動清掃を有効化し、旧キャッシュ10件と
期限切れHTTP利用記録10件の実削除を確認した。移行バックアップ1件は確認済みの作成日時の下限で
登録し、旧NULL owner監査18件・当日利用上限を保持した。これは内部の自動処理開始の実績であり、
削除依頼の受付・本人確認・返信や一般招待開始の受入完了とは区別する。
詳細と未確認範囲は[公開前チェック](beta-release-checklist.md)を参照する。

## 利用者への案内

監査サービスは質問、回答、要件、任意の参照文を受け取り、意味照合に必要な内容をAnthropicへ
送る。要件の自動生成を選ぶと質問も生成処理に送る。確定した監査は同じ利用者が履歴として
取得できる。機密情報を送る前に、監査運営者とモデル提供者の両方の条件を確認する。

招待キーは認証、本人のAnthropic APIキーはモデル呼び出しだけに使う。モデルキーはHTTPSの
秘密ヘッダーでサービスを経由するが、アプリのDB・招待台帳・監査レポートへ保存しない。
キーはチャット、監査本文、URL、公開Issue、削除依頼に記載しない。サーバー共通キーへ代替しない。
モデル利用料は利用者、ホスティング費は運営者の負担となる。

## 保存対象と期限の案

| 対象 | 内容・目的 | 保持・削除の扱い |
|---|---|---|
| 利用者の監査DB | owner ID、session ID、日時、質問・回答・参照文、要件・生成メタデータ、要件別の根拠と判定、旧診断値、再監査の参照ID | 作成から最大30日。自動化ONでは起動時と23時間周期で29日以上経過した行を削除する。削除依頼は本人確認後7日以内 |
| 利用上限台帳 | owner ID、HTTP時刻、UTC日別開始数、実行中予約、時計の基準値。監査本文・APIキーは含まない | 当日の上限を保持。期限切れHTTP記録・予約と、現在のUTC日より7日を超えて古い日別行を日次清掃する。日別行はUTC日境界と24時間以内の清掃間隔を含め最大9日以内 |
| 招待台帳 | owner ID、招待キーのハッシュ、有効・無効、有効期限 | 招待利用中は保持。利用終了から30日以内に無効credentialを運営者が除去する案。owner IDは別人へ再割当てしない |
| 削除・問い合わせの作業記録 | 受付番号、owner ID、本人確認済みか、対象範囲・期限、作業日時・件数、バックアップ処理状況 | 対応完了後90日で削除する案。復元時の削除再適用と対応確認用。監査本文・秘密キー・本人確認コードそのものは残さない |
| 運営者が管理するDBバックアップ・エクスポート | 障害復旧用のコピー。監査本文を含み得る | 通常は作成後30日以内。削除対象を含むコピーは本体削除後30日以内にも消去する。期限の早い方を採用し、コピーし直して期限を延長しない |
| HTTPのメタデータ・埋め込みキャッシュ | 要件生成・参考診断の一時的な処理 | HTTP監査では共有の永続キャッシュを使わない。旧版の既知形式のファイルは自動化ONの停止中清掃で消去する |

`UGH_RETENTION_AUTOMATION=1` と[対応する起動方法](invite-beta-deployment.md#日次削除の自動化)で、
監査・利用台帳・アプリの登録済み移行バックアップ・既知の旧キャッシュを自動清掃する。
子のHTTPプロセスを停止・回収してから清掃し、成功後だけ受付を再開する。期限の余裕は1時間以内で、
停止や清掃の異常時は再開しない。ホストの再起動時も起動前清掃を通す。
HTTPの子も親の生存と稼働期限を監視し、親の異常終了後に受付を継続しないよう、
終了通知後の最大30秒で強制停止する。子が実際に終了するまでは次の清掃を開始させない。
直近成功の件数・日時・次回期限は監査DBに隣接する `.retention.json` へ記録する。
招待・問い合わせ記録・別エクスポート・クラウドのコピーは対象外で、担当者が別途管理する。
日次記録の途切れやホスト自体の停止は運営者が点検し、期限超過と原因を解消してから受付を再開する。
利用上限台帳の通常の古い行削除はアクセス時に行われるため、無アクセスでも日次清掃が必要。
監査本文の削除で当日の上限を返却しない。招待失効だけでも監査データは削除されない。

`owner_id=NULL` の旧記録は移行前の運営者管理データであり、招待利用者には表示しない。
今回の利用者向け期限削除CLIも対象にしない。保有理由と別の処分計画を運営者が記録する。
利用者の依頼を根拠に、所有者不明の記録を推測して削除・割当てしない。

## 削除依頼・問い合わせ窓口

**運営者提供ベータの非公開窓口：[kkoo6798@gmail.com](mailto:kkoo6798@gmail.com)。**
運営者が2026-10-29に掲載先として指定した。メールボックスの受信・送信実績は確認済みだが、
個別削除依頼の受付・本人確認・返信の実演、担当者、適用開始日は未確定で、
これらが揃うまで一般の招待開始を保留する。自己ホスト版は各運営者の窓口を使う。
公開GitHub Issueは合成データによる不具合報告用で、
個人の監査・削除依頼を受ける場所ではない。

受付後の手順は次のとおり。

1. 受付番号を付け、希望範囲（全履歴か特定の監査か）と招待時の連絡先を非公開で確認する。
2. 招待発行時に登録した連絡先とowner IDを照合し、その連絡先へ確認コードを返して本人確認する。
   owner IDや監査IDだけを本人確認としない。本人確認のためAPIキーや招待キーを送らせない。
3. 本人確認日時と、その日時から7日以内の本体削除期限を記録する。本体削除後は実際の削除日時を
   起点として30日以内のバックアップ消去期限を記録し、作成日からの期限が早ければそちらを使う。
   招待終了を希望する場合は失効も別作業として扱う。失効済み利用者の依頼も登録連絡先で確認する。
4. 下記の停止中メンテナンスで対象と件数を確認し、削除・再取得不能の確認結果を非公開で返信する。
   本体の削除完了とバックアップ消去完了は区別して通知する。

現行CLIはowner単位または期間による削除用。特定の監査だけの依頼を全履歴削除に勝手に拡大しない。
必要な範囲がCLIで表現できなければ、個別の確認済み手順を用意してから実施する。
本人確認が完了しない依頼は削除せず、不足点を返信する。無期限に放置せず受付記録で追跡する。

## 運営者の停止中メンテナンス

本番での初回削除前に、合成データのDBコピーで対象・他利用者の保持・復元時の再削除を検証する。
実際のDB、利用台帳、バックアップ、キャッシュの絶対パスを確認する。以下は配置例であり、
別プロジェクトのDBや所有者不明の記録を対象にしない。

1. 監査受付と自動デプロイを停止し、全アプリプロセス・実行中監査の終了を確認する。
   接続元を塞いだだけでは実行中の書き込みが止まったことにはならない。
2. 対象件数を既定のdry-runで確認する。owner IDは非公開の管理情報として扱う。

```bash
python -m ugh_audit.retention --db /data/audit.db --older-than-days 29
python -m ugh_audit.retention --db /data/audit.db --owner alice
python -m ugh_audit.retention --usage-db /data/usage.db
```

3. 対象の一方を選び、停止を実際に確認してから適用する。期限清掃とowner削除は別の操作。

```bash
python -m ugh_audit.retention --db /data/audit.db --older-than-days 29 --apply --service-stopped
# 本人確認済みの全履歴削除の場合は、上の期間指定を --owner alice に置き換える。
python -m ugh_audit.retention --usage-db /data/usage.db --apply --service-stopped
```

`--service-stopped` は運営者による確認の申告で、OS上のプロセス停止を検出する機能ではない。
監査DBモードは起動前処理と同じlockを使う。利用台帳モードは独自のlockであり、起動前処理と
共通ではない。両モードのSQLite排他も、実際の停止確認の代わりにはならない。
監査DBと利用台帳は別々の処理で、両方を一括でロールバックする機能はない。
SQLiteの削除・圧縮処理と整合性確認を行うが、ストレージ装置やホストの複製からの物理消去を
証明するものではない。失敗時に `deletion_committed=true` なら削除済みの可能性があるため、
受付を再開せず状態を確認する。旧バックアップをそのまま戻して削除を取り消さない。

4. 利用者データを含み得る旧キャッシュを停止中に確認し、必要なファイルだけを消去する。
   例は `/data/embedding_cache.npz` と旧 `/data/meta_cache/`。設定変更だけでは既存ファイルは消えない。
   HTTPのキャッシュ迂回に加え、公開ホストでは `UGH_AUDIT_EMBED_CACHE_DISABLE=1` を設定する。
5. 削除記録を更新し、バックアップの期限処理を行う。retention CLI単体はバックアップ・招待台帳を削除しない。
   自動supervisorは登録済みの移行バックアップを別処理で清掃する。
6. 整合性と対象件数を再確認後に起動し、認証・対象履歴が取得できないこと・他利用者の参照を確認する。
   当日の上限をリセットせず、監査内容のコピーを作業ログへ残さない。

## バックアップの期限・復元

`deployment-backups/` はスキーマ移行時にアプリが作るコピーで、クラウドのボリュームバックアップと
別に管理する。2026-10-29の本番確認ではRailwayのボリュームバックアップは0件、自動スケジュールも
未設定だったが、アプリ側の移行前バックアップは別途存在する。「バックアップがない」とは扱わない。

アプリの登録済み移行コピーは、manifestの保持起点から29日以上経過したものを日次自動清掃する。
保持起点・内容のハッシュ・サイズを検証し、mtimeやコピーで期限を延長しない。旧コピーには、
独立した証拠から確認した作成日時以前の下限を明示登録し、正確な作成日時とは区別する。
未登録コピーや未知ファイルがあれば削除せず起動を止める。

運営者は、アプリの移行前コピー、運営者のエクスポート、クラウドのスナップショットについて
作成日・保存先・期限・対象削除の有無を一覧化する。期限に達したコピーを明示的に削除し、
バックアップがさらに別の場所へ複製されていないことも確認する。自動削除設定がない保存先では
担当者が期限を追跡する。削除処理の直前に、期限のない生データの安全コピーを追加しない。

復元は公開接続を止めた環境でのみ行う。整合性確認後、復元した時点より後の削除記録と
現在の保持期限を再適用し、招待の失効状態・利用上限も確認してから受付を再開する。
復元やコピーでバックアップの期限を延長しない。管理対象のコピーを全て期限内に消去するまで
削除記録で追跡し、削除済みデータを復活させない。
[配備と移行](invite-beta-deployment.md)も参照する。

## 外部サービス・ログの扱い

監査DBの期限はAnthropic、Railway、Agensi、利用者のクライアントや利用者自身の出力保存先へ
自動適用されない。運営者が管理するコピーと、各提供者・利用者が管理するコピーを区別する。
Anthropicの保持には契約・機能・例外条件があるため、BYOK利用者が
[公式のAPIデータ保持案内](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)
と自身の契約を確認する。サービス側の削除で提供者側の削除完了を保証しない。

HTTP監査のアプリログへ監査本文・秘密ヘッダーを出さない設定・実装を公開条件とする。
アプリの例外ログ検査だけで全経路の非記録を保証せず、TLS終端、HTTPアクセスログ、
監視・エラー収集の設定も公開前に点検する。時刻・パス・HTTP状態・接続元情報などはホスト側に
残り得る。Railwayのログ表示期間は契約プランに依存し、プラン変更で古いログが再表示される
場合もあるため、表示期間を物理消去の保証と扱わない。
[Railwayのログ仕様](https://docs.railway.com/observability/logs)と
[バックアップ仕様](https://docs.railway.com/volumes/backups)を確認し、実プラン・実設定を記録する。

Agensiの配信条件と掲載終了後のアクセスは[権利・掲載終了の注意](../marketplace/agensi/rights-and-withdrawal.md)
を参照する。掲載終了だけでUGHの招待や保存データも消えるとは約束しない。
適用開始の確認項目は[公開前チェック](beta-release-checklist.md)にまとめる。
